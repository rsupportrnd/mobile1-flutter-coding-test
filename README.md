# RSUPPORT mobile1 flutter developer test

알서포트 코딩 테스트 참여에 감사 드립니다.
본 테스트는 **AI 시대의 개발 협업 역량**을 검증하기 위해 설계되었습니다.
단순한 구현 능력보다 **문제 정의·판단·검증·협업 흔적**을 더 중요하게 봅니다.

- 작성된 코드와 커밋/PR 서술은 인터뷰에서 함께 리뷰됩니다.
- 과제를 끝까지 완료하지 못해도 괜찮습니다. **문제에 접근한 과정과 판단 근거**가 더 중요합니다.

## 1. AI 활용 정책

**AI 도구(ChatGPT, Claude, Copilot, Cursor 등) 사용은 전면 허용·권장합니다.**
다만 아래 원칙을 지켜주세요.

| 항목 | 원칙 |
|---|---|
| 허용 범위 | 설계 토론, 코드 생성·리팩토링, 디버깅, 문서 작성 모두 허용 |
| 기록 의무 | **사용한 주요 프롬프트/대화 맥락을 남겨주세요.** 방법은 자유 — 커밋 메시지, `AI_NOTES.md`, PR 본문 등 |
| 비밀 업로드 금지 | API 키·토큰·사내 코드를 AI에 업로드하지 마세요. 샘플로 대체하세요 |
| 검증 의무 | AI가 생성한 코드를 **그대로 제출하지 마세요.** 직접 읽고 테스트하고 의도대로 고쳐주세요 |
| 라이선스 | AI가 끌어온 외부 코드·이미지의 라이선스를 확인해주세요 |

> 면접에서는 "AI에게 무엇을 어떻게 시켰는지"와 "AI 산출물의 어떤 부분을 어떻게 고쳤는지"를 질문할 예정입니다.

## 2. 수행 가이드

- **권장 시간**: 4~8시간 (주말 중 한나절 ~ 하루)
- **범위 조정 자율**: 요구사항 전부를 구현할 필요는 없습니다. 선택한 scope와 제외한 이유를 PR에 기록해주세요.
- **막혔을 때**: 고민한 흔적을 남기고 진행 가능한 다음 단계로 이동하는 편이 낫습니다. 마지막에 "막힌 지점과 가설"을 PR에 써주세요.
- **해결 수단**: 언어 · 프레임워크 · 플랫폼 · 빌드 도구 선택은 **완전 자유** 입니다. 저장소에 포함된 Flutter 시드는 참고용 스타터이며, 필요 시 교체·삭제하셔도 됩니다. 선택한 스택과 이유를 PR에 기록해주세요.
- **실행 환경**: 과제 특성에 맞게 Android / iOS / Desktop / Web 중 가능한 조합으로 확인. 동작 확인 환경을 PR에 기록해주세요.
- **품질 게이트**: 본인 스택에 맞는 lint/format/test를 돌리고, 제출 전 통과하는 상태로 만들어주세요.
- **CI**: 필수 아님. 원한다면 본인 스택에 맞게 자유롭게 구성해주세요 (가산 요소).

## 4. 과제 목록 (하나 선택)

회사의 관심 기술 탐색을 주제로 선정했습니다. **원하는 주제 하나**를 골라 진행해주세요.
각 과제는 "전체 구현"이 아닌 **"프로토타입 수준에서 핵심 판단을 보여주는 것"** 을 목표로 합니다.

> 과제에 등장하는 특정 API(예: `MethodChannel`, `Flutter Desktop`)는 **예시**입니다. 본인 스택의 동등 수단으로 풀어도 됩니다. 선택한 수단과 이유를 PR에 기록해주세요.

### ① 내장 카메라앱 클론
- 전면/후면 카메라 프리뷰를 비율대로 표시
- 회전 대응:
  - 시스템 상태바는 회전 반영 (위치로 확인 가능)
  - 앱 UI 레이아웃은 고정, 단 **셔터/설정 아이콘 등**은 기기 방향에 따라 **애니메이션 회전**
- 기대 수준: 프리뷰 표시 + 회전 애니메이션 동작

### ② 플랫폼 핑거프린팅
- Android/iOS 각 플랫폼별 기기 식별 데이터 생성
- **플랫폼 공통 추상화 패키지**(예: `device_info_plus`) 대신 **네이티브 계층을 직접 호출** 권장 (예: Flutter `MethodChannel`, React Native Native Module, Kotlin/Swift 직접 구현 등)
- 데이터는 **해시 처리**
- 식별이 어려운 값이 있으면 대체 수단을 선택한 근거를 남겨주세요
- 기대 수준: 네이티브 계층 직접 호출 + 해시 처리된 식별자 출력

### ③ 커스텀 파일 피커 (Windows/macOS)
- 시스템 파일 Picker 및 스택의 고수준 파일 선택 라이브러리 **미사용**
- 메인 윈도 버튼 → 별도 피커 창 오픈
- 메인앱과 피커가 **하나의 앱 안에서** 동작 (별도 실행파일 금지)
- 기대 수준: 멀티 윈도 오픈 + 파일 선택 결과가 메인 윈도로 돌아오는 흐름

### ④ AirPlay 수신 (Android 태블릿 → Mac 화면 미러링 수신)
- Android 태블릿을 macOS의 외부 디스플레이로 활용
- AirPlay 프로토콜 전체 구현이 아닌, **기존 오픈소스 리시버 연동** 중심
- 오픈소스 활용 권장
- 기대 수준: 오픈소스 리시버를 앱에 연동하여 최소 1프레임 이상 수신 확인

### ⑤ 모바일 레이저 포인터
- 모바일 앱: 센서 데이터를 PC로 전송
- PC 앱 (예: Flutter Desktop / Electron / 네이티브 등 자유 선택): 데이터를 **빨간 점으로 표시**, 다른 프로그램 위에 오버레이 표시
- 기대 수준: 센서→네트워크→빨간 점까지 end-to-end 동작 (오버레이는 프로토타입 수준 허용)

### ⑥ 카메라 뷰 인물 중앙 고정
- 카메라 프레임에서 인물이 한쪽에 치우쳐도, 렌더링되는 뷰에서는 **항상 중앙**에 위치하도록 실시간 보정
- 얼굴 인식 오픈소스 활용 허용
- 기대 수준: 얼굴 검출 + 중앙 보정 렌더링이 움직이는 상태에서 유지

### ⑦ PC 사운드를 모바일로 전송
- PC에 가상 사운드 출력 장치 연동 (예: Windows: VB-Cable, macOS: BlackHole)
- PC 플랫폼은 **Windows / macOS 중 자유 선택** — 선택 이유를 기록해주세요
- 캡처된 오디오 스트림을 모바일 스피커/블루투스로 출력
- **네트워크 프로토콜 선택과 근거**에 중점
- 기대 수준: PC 가상 장치 캡처 + 모바일 재생까지 한 방향 스트림 동작

## 5. 제출 절차

1. 이 저장소를 **Fork** 합니다.
2. Clone 후 과제 브랜치에서 작업 (`feature/<과제-키워드>` 권장).
3. 커밋을 의미 있는 단위로 쪼개서 push.
4. Fork 저장소에서 **원본 저장소로 Pull Request** 를 생성합니다.
5. PR 본문은 `.github/PULL_REQUEST_TEMPLATE.md` 양식을 채워주세요.
6. PR 링크를 담당자 메일(**recruit@rsupport.com**)로 회신합니다.

PR 본문에는 다음이 반드시 포함되어야 합니다:
- 선택한 과제와 **scope 결정 근거**
- 설계 선택과 **트레이드오프**
- 선택한 스택과 이유
- **AI 활용 내역** — 도구 / 주요 프롬프트(실패 사례 포함) / 검증 방법 / 수정 지점 / AI 미사용 판단
- 동작 영상 또는 스크린샷
- 막힌 지점·가설 (있다면)
